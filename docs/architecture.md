# Architecture

History summaries overlap-deduplicate the rolling `correction_events` trail before counting keys. A typo-to-corrected-preedit pair is confirmed only by a `terminal=1` record ending in candidate selection or raw-English commit; intermediate per-key snapshots and Escape remain context rather than repeated learning evidence.

Every delivered key press relevant to supervision remains in the in-memory correction trail. Release events are ignored except for model-trigger debouncing. Active-request serialization and atomic replacement are coalesced to at most once per 250 ms, non-terminal general-history snapshots are sampled at most once per 2 seconds, and every terminal training snapshot is retained. A terminal boundary bypasses the coalescing delay, while `supervision-last.tsv` is written only for a completed request. The supervision window caches history/model metadata during live typing and refreshes that heavier context only periodically or after explicit analysis.

Pinyin split checks use immutable first-letter buckets for pinyin syllables and known English tokens instead of rescanning the complete unit table at every recursive step. Requests containing an embedded known English token skip both LibIME and libpinyin sentence lookup and use the system mixed-composition path; libpinyin's bigram search cannot interpret those tokens and previously added latency without useful candidates.

TiPE currently has three main layers: a pure state machine, an fcitx5 engine addon, and a TiPE-owned fcitx5 UI addon.

`State` is a pure C++ state machine. It owns preedit text, candidate lookup, and commit decisions. It has no fcitx5 dependency, so it can be tested without a Wayland session.

`Dictionary::lookup()` loads an optional user dictionary from `~/.local/share/tipe/user-dictionary.tsv` or `TIPE_USER_DICTIONARY`. `Dictionary::learnUserEntry()` updates that private dictionary under a shared advisory lock, validates bounded pinyin/UTF-8 candidate fields, writes a mode-`0600` sibling temporary file, fsyncs it, atomically renames it, and refreshes the calling instance immediately. Its preferred base backend is LibIMEPinyin with the system `sc.dict` and `zh_CN.lm`, which supplies mature segmentation and sentence scoring. TiPE bounds that decoder before constructing its segment graph: complete pinyin and inputs up to eight letters enter LibIME, while a longer unsegmentable typo stays on the bounded system-dictionary and learned-correction paths. This prevents missing or transposed keys from producing an exponential synchronous decode without removing mature sentence scoring once the sequence becomes valid. Accepted LibIME candidates feed their original word segmentation into `UserLanguageModel::history()` and persist separately to `~/.local/share/tipe/libime/user.history`; the bounded mode-`0600` history and lock use the same atomic writer and never modify fcitx5-pinyin's history. The learning-panel protocol reports this automatic layer as `panel<TAB>learning<TAB>dictionary-history` with `ready`, `waiting`, `disabled`, or `error` status, without loading the history or invoking TiP. The decoder and its bounded lookup cache are shared across all `State` instances, and a successful history update invalidates that cache before the next lookup. Libpinyin remains the fallback decoder when LibIME is unavailable or cannot serve a request.

Installed Rime pinyin dictionaries still provide weighted exact words. On the normal LibIME path their contribution is bounded, and TiPE does not run its mechanical phrase composer, so rare Rime tails and ad hoc chunk combinations cannot swamp the language model. Rime composition remains enabled for mixed English-token input, an explicit `TIPE_SYSTEM_RIME_DICTIONARY` override, or a no-LibIME fallback. Parsed Rime rows and indexes are shared by file path, size, and modification version. Historical feedback sentences live only in `tests/fixtures/state-dictionary.tsv`; production keeps a minimal built-in fallback. `State::refreshCandidates()` can surface English-like raw text in two steps: a visible `raw-offer` candidate for unlearned English-shape identifiers, then a first-rank `raw` candidate once the behavior model says raw text should win. The provisional offer is gated by pinyin-tail completion, preventing unfinished pinyin such as `shuruf` or `zenm` from temporarily acquiring a raw candidate.

`InputModel` is the local behavior model. It records recent meaningful key actions in memory, including letters, accepted alphanumeric-token digits, backspace, delete, space, enter, escape, pass-through observed keys, candidate selection, raw commits, cursor movement, and rerank requests. It also keeps recent committed text for clicked model context and bounded segment-selection chains. Engine reset handling separates that bounded session context from disposable composition state: a normal post-commit fcitx reset can replace `State` without losing the next request's recent commits or correction trail, while `InputContextDestroyed` still removes both. Some keys are observed even when no preedit is active, but TiPE does not accept them, so the focused application still receives them.

`PassThroughSupervisor` extends that vocabulary to TiPE's internal English mode without turning English into a second fcitx5 input method. TiPE stays active, returns every ordinary English key press to the application unchanged, and tracks only a 64-byte current token plus the existing bounded event trails. A Chinese composition that exists at the mode boundary remains visible but frozen; returning directly to Chinese restores the same state, while the first printable English key commits the frozen preedit through `State::commitRawPreedit()` before pass-through tracking begins. Space, Enter, Tab, and punctuation produce terminal raw-English samples. Leaving English mode, resetting or destroying the input context, and changing focus also seal a nonempty known token as a terminal sample, so a final word is not lost merely because it had no trailing space. Backspace, Delete, and in-token Left/Right edits update the bounded token; navigation outside its known bounds drops uncertain token state instead of reading or guessing application text. `tipe-toggle` requires stable fcitx activation, atomically replaces `$XDG_RUNTIME_DIR/tipe/input-mode` (or the cache fallback) with a mode and unique request token, then waits for the engine to atomically mirror that pair in `input-mode-applied`. The engine closes its startup read/watch race by refreshing once after inotify registration. No desktop notification is emitted, so TiPE's own compact mode indicator is the only successful-switch feedback. A no-argument invocation activates inactive/non-TiPE sessions in Chinese mode and toggles the saved mode only when TiPE is already active.

The observed stream is complete for keys delivered to the active fcitx5 input context, not for compositor-reserved global shortcuts that never reach an input method. TiPE turns its niri-owned mode switch into an explicit `ModeSwitch` boundary and listens for fcitx focus/lifecycle events, so unavailable shortcut events cannot accidentally concatenate otherwise separate tokens.

Input contexts carrying fcitx5 `Password`, `Sensitive`, or `Disable` capabilities are excluded before either the Chinese state path or English pass-through path. The engine watches capability changes, drops owned composition/session/snapshot state without a terminal write, invalidates pending model results, suppresses TiPE popups, avoids surrounding text, and leaves press/release events unfiltered. Snapshot writers, deferred rendering, status rendering, state restoration, and asynchronous model-result application repeat the same gate as defense in depth.

Passive `Space` or punctuation commits of the already-leading candidate remain supervision events but do not persist ranking preferences. Explicit navigation, numbered/mouse selection, validated model output, raw-English repetition, correction evidence, and confirmed segment chains are durable evidence. Old one-count candidate rows remain readable but do not override the base model. Raw key and candidate evidence stays only in the bounded supervision cache; persisted last/history snapshots remove surrounding text and cross-commit context. Requests also carry stable `context_features` and `surrounding_features` fingerprints; those opaque rows survive sanitization so an explicitly enabled offline export can learn context without retaining its original text. The preference file uses locking and atomic replacement, and `tipe-check-preferences` validates it without mutation.

The installed model adapter mirrors that event vocabulary in heuristic mode, so digit-bearing correction trails such as `qwen2`, full delete, then `qwen3`, or in-preedit edits such as moving left to insert `i` into `nhao` or using `Delete` to turn `niyhao` into `nihao`, can be forwarded as `correction<TAB>typo<TAB>corrected-preedit` without requiring a cloud model. It also consumes matching `segment_chain` rows, promoting the combined candidate when it is already in the current candidate list, promoting the suffix candidate when the request is for the remaining preedit after a prefix commit, and returning a validated correction when the chain implies one. Its raw-English ordering follows fixed tokens or learned preferences rather than focused-app differences. For llama.cpp and OpenAI-compatible local or cloud backends, the adapter adds `supervision_mode`, a top-level `learning_status`, and a structured `behavior_summary` to the JSON prompt. Local backends receive the bounded recent-event data by default. Cloud modes selected through `tipe-model-current` receive only the active preedit, candidates, and current candidate UI state unless `TIPE_MODEL_SEND_RECENT_INPUT=1`; that opt-in adds recent event counts, correction trails, history evidence, and compact supervised learning signals. `TIPE_MODEL_SEND_SURROUNDING=1` independently adds cursor-surrounding text and the application name. `learning_status` classifies a clicked request as keyboard-context-only, ready-to-learn, awaiting-suffix-confirmation, selected-candidate-already-top, rank-only, or no-action and lists the supported protocol rows that are already safe to consider. `supervision_mode=pass-through-only` tells a model that an empty-preedit request is useful keyboard behavior context only, not an invitation to generate candidates from nothing or inspect unrelated persisted learning rows.

An English pass-through request may carry its bounded raw token even though `supervision_mode` remains `pass-through-only`; `runtime_state input_mode english` distinguishes it from empty keyboard context. Adapters and generated wrappers treat that token as read-only behavior evidence, not an active candidate-generation request.

Realtime exact correction and the heuristic adapter share the same conflict rule: only a unique highest-count correction for one typo is automatic. Tied strongest corrections are retained as supervision evidence but produce no automatic candidate correction until later behavior breaks the tie. Generalized omission/extra/replacement patterns are used only when there is no direct exact correction record for the current preedit. Global keyboard habits may repair a merely composable phrase, but cannot override an exact known pinyin entry, existing Chinese selection evidence for the same spelling, or a non-pinyin English token already committed as itself. A generalized repair must preserve the shortest parsed pinyin-syllable count and produce either a known word or a decisive language-model result; otherwise the original composition wins.

Cloud requests are the privacy exception to the full external-model history flow below. With both cloud-sharing permissions off, serialization removes recent events, correction trails, recent context, segment chains, known preferences/corrections, history summaries, cursor-surrounding text, and the application name before JSON is built. The request retains only the active composition, bounded candidates and candidate metadata, and current candidate UI state. Local backends and explicitly opted-in cloud requests can still use the broader bounded summary.

The model request event window is intentionally short and includes broad key context for ranking. After a full commit or cancel, the next empty-preedit pass-through key or next new preedit starts a fresh short `events` window, so a post-commit arrow/Delete/Space supervision request does not inherit the previous composition's letters or candidate-selection event. Correction learning has a separate longer trail that records letters, accepted alphanumeric-token digits, delete/backspace, space, enter, pass-through keys, cursor movement, rerank requests, and commit/clear boundaries, so a clicked model wrapper can see a wider behavior sequence. The current and last live supervision requests are written under `$XDG_CACHE_HOME/tipe/`, or `~/.cache/tipe/` when `XDG_CACHE_HOME` is unset, and TiPE also appends the same request protocol to a bounded `supervision-history.tsv` file with a compact time/program/preedit header. That history is trimmed automatically to roughly 256 KiB, giving clicked analysis a recent behavior stream without running a background model forever or letting raw key data grow unbounded. The window/replay helpers extract the latest complete request from history when current and last snapshots are unavailable, so manual Analyze can still inspect the most recent supervised behavior after a composition has cleared. The learning panel additionally summarizes recent history records into stable `panel<TAB>history` rows for common preedits, selected candidates, preedit-to-selected-candidate pairs, applications, key counts, correction-event counts, repeated typo-to-corrected-preedit pairs reconstructed from correction trails, and segment-chain totals; passive default candidate-0 highlights, records marked `supervision_state mode pass-through-only`, and prefix-only candidate selections are excluded from full-preedit selected-candidate history so the panel does not present ordinary initial ordering, empty-preedit keyboard context, or a partial commit as learned user choice for the entire preedit. `tipe-model-adapter` includes the same bounded summary as `recent_history_summary` in external model prompts, generated custom wrappers expose it as `recent_history_*` variables and `wrapper-debug` rows, and the offline heuristic adapter can promote a repeated current-preedit pair after it appears at least twice in recent active-preedit history. The panel protocol also emits `panel<TAB>learning<TAB>status...` rows that mirror the adapter/wrapper learning status vocabulary, so the GTK supervision window can tell the user whether the current click is ready to learn, waiting for a suffix candidate, only ranking, or only carrying empty-preedit keyboard context. The GTK learning/supervision/analyze windows render those rows with Chinese-first labels for user-facing status and evidence, while preserving raw protocol rows such as `preference<TAB>...`, `correction<TAB>...`, and `segment_chain<TAB>...` where copying or wrapper debugging requires exact tokens. The paired preedit/candidate history is the stronger ranking signal because it preserves what input string led to what explicit choice instead of only reporting global candidate frequency; it also covers raw-English habits such as repeatedly selecting `start` for preedit `start` without adding word-specific rules. Repeated correction trails are treated the same way: when recent active-preedit history repeatedly shows a plausible full-delete-retype, partial rewrite, or middle-edit correction, the heuristic adapter can emit a `correction<TAB>typo<TAB>corrected-preedit` row when either side of that repair matches the current preedit, and HTTP dry-run prompts expose the same evidence as `recent_history_summary.top_corrections` plus a `history_correction` supervised learning signal. The built-in correction learner still interprets only the safe subset it understands, so noisy pass-through keys such as arrows and tabs do not evict the typo/deletion pattern before it can be learned. The correction learner watches for practical patterns: the user types something, fully deletes it with Backspace or cursor-positioned Delete, then types and commits a similar corrected preedit; the user backspaces to a shared prefix and rewrites the rest before committing; or the user edits the middle of the preedit with cursor movement plus insertion/Delete before committing. After repeated observations, TiPE can borrow candidates from the corrected preedit, such as offering `nihao` candidates for learned `ihao`, `nhao`, or `niyhao` omissions/extra-letter corrections. Segment-selection chains are a separate supervised signal: when the user commits one or more prefix candidates from a longer preedit and then confirms the final candidate, TiPE records the original preedit, all consumed prefix pinyin, all committed prefix text, remaining preedit, corrected full preedit, and combined candidate. This covers ordinary chunking such as `jixuzuo -> 继续 + 做`, character-by-character rare phrases, and typo-repair chunking without adding word-specific rules. One complete chain remains staged unless active prefix evidence makes it safe to offer immediately; after the same chain is confirmed twice, a safe non-ASCII combined phrase is atomically published to the private user dictionary and becomes available immediately. Persisted behavior data is bounded: TiPE keeps the strongest candidate preference rows and correction rows when saving, writes them to a temporary file first, and then atomically renames that file into place. Live segment-chain recording, model-output learning, preference loading, and `tipe-check-preferences` all reject malformed rows and implausible implied corrections, so a damaged TSV file cannot silently poison ranking.

Terminal snapshots are additionally written to a separate `supervision-training-history.tsv`. Unlike the 256 KiB general debugging history, it receives one record only after candidate selection, raw commit, or cancel, retains up to roughly 1 MiB, and trims only at complete record boundaries. Repeated choices are intentionally retained as frequency evidence. This prevents per-key intermediate snapshots and repeated long trails from evicting the examples needed for user-specific model work, without adding I/O to each ordinary key event.

`tipe-training-export` is the offline bridge from bounded supervision history to model development. It prefers the terminal training history when present, emits one structured `tipe.training.v1` JSON object per sample, separates the terminal user action into `target`, and retains prefix-consumption metadata. Repeated equivalent terminal choices remain separate samples because frequency is user-preference evidence; `--deduplicate` is available for evaluation sets. Its default privacy boundary excludes application names, the longer correction trail, known persisted evidence, recent-commit context, and surrounding context. `--include-context` and `--include-surrounding` expose only bounded stable fingerprints, never the source text; application names remain a separate `--include-application` opt-in. The advanced model settings store the two TiP-training fingerprint choices independently of the cloud-request permissions and pass them only to an explicitly clicked personal-model training action; all four choices default off. When personal mode uses a custom model path, that same path is passed as the training output so clicked training and clicked analysis cannot silently use different artifacts. The exporter is read-only and never invokes a backend, so collecting data remains lightweight while local, cloud, or hand-built model training can happen as a separate user-controlled step.
Evidence-enabled export also removes preference and completed segment-chain rows that exactly match the terminal target. Frequency still survives as repeated labels and bounded pair hashes, while a row persisted by the action being predicted cannot become an input feature for that same action.

Personal training separates ranking and correction supervision. Records with at least two candidates train the hashed pairwise reranker. A one-candidate English raw record cannot establish a ranking comparison, but its delete/retype and cursor-edit trail still trains position-aware correction patterns and position-independent key habits. A correction-only model can therefore become useful before enough explicit candidate choices exist, and its artifact reports both sample counts.

The in-process correction path recognizes missing, extra, replacement, and adjacent-transposition edits over pinyin up to 16 bytes. Exact typo pairs activate locally at count two. Generic position-aware patterns require 2 observations for missing/transposed keys, 3 for extra keys, and 4 for replacements. Position-independent habits require 3 observations for transposition, 5 for a missing key, and 6 for extra/replacement keys. TiP prediction, runtime distillation, C++ loading, `tipe-check-preferences`, and doctor use the same per-kind thresholds. Legacy files without published rules may still derive repeated positional patterns from exact pairs. Active model rules can repair unseen positions and combine two different strong omissions, while known English identifiers remain inert. Candidate generation and dictionary lookup are bounded, so ordinary refresh runs no Python or external model.

`tipe-personal-model-train` trains TiPE's own model, **TiP**, from that dataset. It runs only when requested, exports the longer correction trail and validated correction evidence already present in terminal snapshots into a temporary private dataset, and trains a bounded model with five components: a hashed pairwise Chinese candidate ranker, a personal keyboard error channel, hashed exact English-token memory, an independent raw-English offer classifier, and a compact pinyin prior. Candidate selections and raw-English commits are both terminal supervision. The newest 512 confirmed alphanumeric commits from `pass-through-only` mode with exact `raw-pass-through` candidates supply quarter-weight auxiliary positives to the English profile and exact-token evidence, but they never count toward the generic capability gate. Only real Chinese-mode competition rows whose metadata marks the exact preedit candidate as `raw-offer` supply the accepted/rejected validation classes, and zero false raw promotions remain mandatory. A prefix selection from a longer preedit is transformed into an exact consumed-prefix sample, such as `jixu -> 继续`, and is compared only with candidates carrying the same `consumed_prefix`; whole-sentence candidates cannot become false negative labels for that partial choice. Repeated snapshot copies of one persisted correction are collapsed to their strongest stored count instead of being counted once per snapshot. Personal candidate/preedit strings, ordered trails, context, and exact English tokens are represented by hashes rather than retained verbatim in the model file. Aggregate one-edit rules retain only the changed letters and positions, while the compact prior retains public pinyin spellings and log-frequency buckets loaded from configured Rime dictionaries. New artifacts include the validated `name` value `TiP`; legacy artifacts without it remain compatible. The default hash space is 262144 dimensions to keep accidental high-weight collisions low; the artifact remains sparse and serializes only non-zero weights, so the larger index space does not allocate or write a dense vector.

The reranker features include the current preedit/candidate pair, candidate source, rank, prefix/partial status, key-event counts, correction-trail counts, supervised `preference`/`segment_chain` evidence, and bounded operation order. Training consumes the ordered key/action chain attached to every terminal outcome, not only records containing one complete pinyin token. Feature version 4 retains the version-3 ordered and opt-in context-fingerprint features, associates up to 24 detailed correction/action events and 32 adjacent transitions with the selected candidate, and adds bounded pinyin-syllable/Chinese-character transfer features. The pinyin alignment accepts only bounded ASCII pinyin and bounded Han candidates; ambiguous boundaries prefer paths without artificial one-letter syllables and then deterministic longest valid boundaries. Prefix-derived samples contribute only their exact pair and these phonetic transfer features, avoiding application, rank, and full-composition event leakage while still letting a character choice inform a later unseen phrase. Only sparse feature indices survive for personal pairs, context, trails, and English tokens; the public pinyin prior and aggregate changed-letter rules are the explicit non-hashed exceptions described above. A separate bounded hash records how often each selected input/candidate pair was observed, without storing either source string. Activated evidence also contributes a capped prior before the promotion-margin gate: normal candidate preferences activate at count 2, raw-preedit preferences at count 3, and confirmed segment chains at count 1. Exact repeated-token evidence remains usable even while aggregate English generalization is locked.

The user installer sends the complete CMake install into a private `DESTDIR`, accepts the final manifest line even when CMake omits its trailing newline, and validates every staged path before replacing live files. Helpers, compatibility libraries, and prefix-rewritten addon metadata are copied to same-directory temporary files and atomically renamed, so fcitx5 cannot fault in a partially overwritten shared object. Normal exit and handled signals remove staging and temporary paths.

Validation is capability-specific. The `capability-isolated-temporal-v4` Chinese generic holdout excludes every request carrying a raw candidate and every sample derived from a longer prefix selection, then requires at least five unseen, unsupported non-leading Chinese choices, at least 60 percent accuracy, and no original-first regression. Derived prefix samples remain available to exact prefix learning and feature-version-4 phonetic transfer, but cannot enter a generic denominator because their labels compare only candidates with the same consumed prefix rather than an independent full-input outcome. The raw-English classifier has a separate balanced temporal holdout with accepted and rejected `raw-offer` examples; it requires at least four of each overall, at least two of each in validation, perfect binary holdout accuracy, and zero false raw promotions. Its sparse classifier weights are trained and validated independently from the candidate ranker, so passing a gate cannot disappear when the final ranker is retrained. Keyboard correction is reported safe only when repeated personal patterns or key habits are backed by the compact pinyin prior. Normal model publication then max-merges bounded pair evidence, correction patterns, key habits, and the pinyin prior from the valid existing artifact into the candidate; it refuses a merge that would discard an active old row. This separates the finite replay window from long-lived learned behavior and prevents periodic retraining from forgetting established evidence. `inspect`, model config, doctor, and the supervision window report all three capabilities independently instead of treating one global `ready` label as proof of every behavior.

At prediction time a non-leading Chinese candidate must beat the current first candidate by the stored promotion margin, default `0.5`, and must also have activated request evidence, repeated exact-pair evidence, correction-source metadata, or the validated Chinese generic gate. Phonetic-transfer and long-trail weights are part of generic ranking, so they cannot reorder an unseen Chinese input until that gate passes; exact evidence and validated keyboard correction remain independently usable. A `raw-offer` can move first through repeated Chinese-mode exact-pair evidence, a hashed English-mode token count of at least three, or the independently validated raw profile; generic Chinese safety cannot unlock it. The English-mode path promotes only the identical token and is suppressed by any active repeated non-raw choice for the same preedit, so explicit correction can reverse passive learning. Generic speculative corrections produced during F9 are merged after the existing first candidate instead of replacing it; a learned correction returned by the model still follows the validated correction path. The correction pass reconstructs full-delete/retype and cursor-edit evidence, reducing single-edit repairs to position-aware patterns and position-independent missing-key, extra-key, replacement-key, or adjacent-transposition habits. It applies the per-kind activation counts above rather than one global minimum. When several complete-pinyin repairs have equal personal evidence, the model consults a compact log-frequency prior and refuses to guess unless the best prior leads by at least two buckets. Personal mode remains behind the explicit model trigger and never runs continuously on every key. Feature-version-1 through version-3 artifacts remain readable, but old validation metadata cannot unlock the new capability gates. Model files use mode `0600`; training does not change the selected backend, while an already active personal backend reads a newly promoted model on its next clicked request.

Full commits, raw commits, prefix commits, and cancels produce a terminal supervision snapshot before composition is cleared. This keeps the original preedit and candidate list paired with the final `candidate-selected`, `raw-committed`, or `escape` event. History-derived preferences require the selected candidate text to match that final event, so arrowing to a candidate and then abandoning it is context, not a learned choice.

Model promotion is monotonic across all three capability gates. If an existing artifact has safe keyboard correction, raw-English profiling, or generic Chinese ranking and a newly trained candidate loses that capability, the wrapper reports `preserved-safe-capability` and leaves the existing artifact byte-for-byte unchanged unless `--force` is explicit. A later, harder validation slice therefore cannot silently disable a previously validated behavior.

Component publication follows the same capability split. While generic Chinese ranking is locked, a below-baseline generic holdout cannot block a keyboard-correction or raw-English component that passed its own gate. The generic weights remain inactive, and max-count merging retains already active evidence and capabilities from the existing artifact.

Legacy validation metadata cannot block cleanup forever. When a candidate uses `capability-isolated-temporal-v4`, has no ordinary first-choice regression, retains safe components, and keeps generic ranking locked, the wrapper may allow one `safe-validation-upgrade`. Version-3 generic safety remains readable because its denominator was stricter; version 4 prevents prefix-derived labels from claiming independent whole-input evidence. A newly validated keyboard or raw-English component may use `safe-capability-upgrade`. Neither label claims Chinese generic readiness.

The training wrapper holds a non-blocking `flock` on a mode-`0600` sibling lock file from before dataset export through the final promotion decision. Concurrent training attempts fail before creating a candidate artifact, while prediction remains lock-free and sees either the old or atomically replaced complete model.

Built-in raw-English behavior is intentionally user-preference based instead of focused-app specific. Known developer tokens, including TiPE itself, are available everywhere, and repeated raw commits can teach TiPE to put an unknown identifier first everywhere. Explicit raw learning uses generic non-pinyin terminal and letter-pattern rules rather than a per-example learning exception, while preserving `er` and common `lv`/`nv` pinyin forms. Automatic typo-pattern suppression uses a narrower English test, so an unfinished pinyin tail such as `xuesh` can still benefit from learned missing-letter correction. Raw commits that still look like ordinary pinyin remain supervised events but do not become durable raw-English preference rows or HTTP `known_preferences`; this keeps historical rows such as `nihao -> nihao` from misleading a clicked model. The focused application string and bounded surrounding text are still included in explicit model requests for user-selected external models, but the built-in heuristic does not make different windows produce different default raw-English ordering.

Once the first candidate is the raw preedit, `State` treats subsequent digit keys and token symbols (`-`, `_`, `.`, `/`) as raw-token continuation instead of candidate selection or punctuation commit. An uppercase ASCII letter during an active composition also enters this mode, preserves the existing text and letter case, and updates the candidate panel without committing Chinese; an uppercase letter with no composition remains an observed application passthrough. The raw-preedit mode is deliberately tied to the current composition and is cleared with reset/commit/empty deletion, so ordinary pinyin such as `nihao` keeps numeric candidate selection and normal punctuation behavior.

Model choice is intentionally outside the core input method. Built-in local learning is always available and offline. `InputModel::rerankCandidates()` retains an explicit `allowExternalModel` gate for probes and replay, while the live engine keeps continuous mode local-only and handles `F9` asynchronously. It captures the pre-rerank TSV request, expands the unchanged candidates for immediate feedback, and invokes the configured command on a worker; only the final model ordering is rendered. If no model command is configured, the local rerank remains immediate. Rapid repeated `F9` events are debounced without invalidating the active request. Completion wakes the fcitx event loop through an eventfd; the result is accepted only when the input context and the armed preedit/candidate/cursor state are unchanged. Any later non-debounced key, candidate click, selection, clear, or destroyed context invalidates the request. The snapshot includes current preedit, focused application and bounded surrounding text when available, candidates and candidate metadata, UI/runtime state, recent key and correction trails, recent commits and segment chains, and bounded learned evidence. Before composition is cleared, terminal commit/cancel snapshots retain the original preedit, candidates, actual committed index, and final event trail. Commands are executed directly through `posix_spawnp`, not through a shell, with a bounded output buffer and timeout. Each invocation owns a process group, so a timed-out wrapper also terminates child processes such as `curl` or a local model runner instead of leaving them behind.

TiP training is the clicked model-update path, not a per-key subprocess. In addition to atomically publishing the bounded model artifact, it distills confirmed English-mode exact-token counts, active positional correction patterns, and active global key habits into dedicated runtime preference rows. The distiller excludes complete pinyin from raw-token memory, publishes only correction components that passed the keyboard-safety gate, is idempotent, migrates earlier inactive normal raw rows, and acquires the same `.lock` file used by the C++ preference writer before atomically replacing the TSV. `InputModel` loads these components into separate bounded maps. Normal typing applies them as an in-process noisy keyboard channel: positional patterns receive stronger evidence, global habits can move to unseen positions, and two different strong missing-key habits may combine only on longer input where multiple omissions are plausible. Short tokens stay on one-edit repair. Exact dictionary phrases outrank merely parseable syllable sequences before model evidence is compared, and the first viable correction stops further dictionary work. The output is capped, and no Python, model process, daemon, or network request runs on a key event. Exact typo pairs still activate immediately, but their unvalidated aggregate patterns are used only for legacy files that have no model-published rules. Consequently normal typing can use learned keyboard and exact-English behavior after training while generalized raw profiling and all cloud/local external calls stay behind their independent validation or explicit `F9` boundaries.

The `llama-cpp` backend is deliberately process-per-click rather than a daemon. It creates a private temporary directory, converts the same bounded JSON request into a prompt, starts `llama-cli` with the configured GGUF, CPU thread count, and context size, filters the returned protocol, removes the prompt/output files, and exits. Signal and error cleanup remove the private files too. The default is CPU-only (`-ngl 0`), 6 threads, an 8192-token context, and a 30-second engine timeout. `tipe-restart-fcitx5` loads `tipe-model-current` by default and passes the configured timeout into the parent fcitx5 process because the engine must know that deadline before the child can source its config. This avoids idle model CPU/RAM use at the cost of loading the GGUF on each explicit analysis.

The installed `tipe-model-config` and `tipe-model-current` helpers select offline heuristic, TiP, one-shot llama.cpp, dump, custom wrapper, Ollama, OpenAI, or another OpenAI-compatible endpoint. `tipe-model-adapter` validates provider output before returning protocol rows. HTTP providers receive the versioned `tipe.cloud-rerank.v1` JSON prompt through one explicit Chat Completions request; continuous mode never enters this path. A directly entered API key travels to the config helper over stdin and is stored in a separate current-user-only file; `model-env` contains only its path, while an environment-variable reference remains available as an advanced alternative. `TIPE_MODEL_SEND_RECENT_INPUT` and `TIPE_MODEL_SEND_SURROUNDING` are emitted explicitly for cloud configs and default to `0`; the request serializer removes disabled categories before building JSON. `tipe-model-dump` captures exact request TSV through a user-only temporary file and atomically replaces its destination; `tipe-model-explain` summarizes it. `tipe-supervision-window` is the main three-page GTK view: plain learning outcomes, progressive model/API selection, and support. Internal evidence and protocol counters are hidden under advanced details. Opening or refreshing it does not call a model; `更新 TiP` updates the local artifact from terminal history, while the separate `分析当前输入` action runs the configured model once and persists accepted safe output. The model form has a local-only validation action and does not test a provider connection or incur a request. Lower-level `tipe-learning-panel` and `tipe-model-replay` remain read-only unless replay and `--learn-output` are explicitly enabled. `tipe-analyze-window` is a shorter manual replay launcher. None of these helpers changes the active input method. `TIPE_RERANK_COMMAND` remains a compatibility alias; without either model command variable, no external process is started.

For HTTP providers, the bearer token comes from either the validated private key file or the selected environment variable. Stored files must be regular, non-symlink, current-user-owned, bounded in size, and inaccessible to group/other users. The adapter rejects CR/LF injection and writes the Authorization header to a process-specific mode-`0600` temporary file consumed by `curl -H @file`; the token is therefore absent from curl's argument vector. EXIT and signal traps remove the file, and the normal success/error path clears the traps after explicit deletion. Loopback integration tests exercise real curl transport, authentication, prompt serialization, unsafe-output filtering, HTTP failure, malformed JSON, and secret-file cleanup without contacting the internet.

`InputModel` tracks the preference file modification time. Ordinary candidate refresh checks it at most once per 250 ms, while explicit rerank and learning writes force a check. Engine, replay, and TiP distillation share `candidate-preferences.tsv.lock`, merge local deltas, preserve published runtime rules, write a process-specific temporary file, and atomically replace the preference file. Replay deduplicates model output and preserves supervised raw-token, correction-pattern, and key-habit rows it does not generate. Counts saturate at 1,000,000, and larger persisted values are rejected. The persisted limits are 2048 candidate preferences, 512 supervised English tokens, 512 exact corrections, 512 correction patterns, 128 key habits, and 512 segment chains. Full-preedit learning uses candidate `consumed_prefix` metadata: only a positive value shorter than the preedit is partial; zero or at least the full length is complete. Active complete Chinese preferences with matching pinyin-syllable/character counts are reinserted when the decoder temporarily omits them; partial and shape-mismatched rows remain evidence only. A complete segment chain becomes a staged candidate after one confirmation when active prefix evidence supports it, and after two identical confirmations its combined phrase is injected, protected during normal ranking, and published to the private user dictionary even when an older system dictionary did not contain that phrase.

Candidate refresh annotates active learned candidates with consumed-prefix metadata before applying learned ranking. This prevents an old full-preedit preference row from moving a prefix-only candidate to index zero and erasing the information that it must leave a suffix active. The complete metadata pass still runs only once for ordinary input; the early pass is limited to candidates with active preference evidence. Model requests apply the same candidate-exists, shape, activation, and full-preedit checks, so stale rows that local ranking suppresses cannot be handed to an external model as actionable evidence.

The model output protocol accepts plain candidate lines for backwards compatibility, plus explicit `candidate<TAB>text`, `correction<TAB>typo<TAB>corrected-preedit`, `preference<TAB>preedit<TAB>candidate<TAB>count?`, and `segment_chain<TAB>original-preedit<TAB>consumed-preedit<TAB>committed-text<TAB>remaining-preedit<TAB>corrected-full-preedit<TAB>combined-candidate<TAB>count?` rows. Candidate rows reorder the current candidate list and are recorded as lightweight preferences only when they promote a non-leading candidate whose preference is not already stored, so an explicit clicked model decision can affect the next same input without turning a harmless echo of the current first candidate into persistent learning. Preference rows let a model explicitly persist a current-preedit candidate preference even when it is not changing the current ranking; when the preedit and candidate are the same English-like identifier, TiPE stores that as a raw-English preference rather than a normal Chinese candidate preference. Correction rows are validated as plausible typo edits, persisted with extra weight, and can refresh candidates immediately, including for typo preedits that originally had no candidates. Segment-chain rows let a model persist a confirmed multi-step selection chain, which later requests can replay as supervised evidence. Runtime model learning and `tipe-model-replay --learn-output` both ignore candidate, preference, correction, and segment-chain rows that only echo learning records already present in the request or preference file, while still allowing those rows to affect the current candidate order. HTTP prompts distinguish newly learnable `suggested_protocol` rows from known `evidence_protocol` rows, so wrappers can use old records for ranking and explanation without treating them as work to output again. This prevents a model wrapper or Analyze replay from self-amplifying old evidence just because TiPE supplied it as context or because a previous replay already learned it. The only additive candidate form is the current preedit itself when it looks like a raw English identifier, which lets local or cloud models promote `started` in a terminal without allowing arbitrary generated candidate text. To keep model requests bounded, TiPE sends at most 16 learned preference rows for the current preedit, 16 matching segment-chain rows, and 32 learned correction rows ordered by current-preedit relevance before global count.

The offline heuristic adapter also turns current UI intent into a learning action: if the model request shows a non-leading `selected_candidate`, the adapter emits both a `candidate` row for immediate reranking and a bounded `preference` row for the current preedit. Prefix-only candidates are excluded from this full-preedit preference path and wait for segment-chain confirmation instead. The core request builder omits inactive candidate preference evidence, and the adapter defensively applies the same thresholds when parsing requests: normal candidate preferences activate at count 2, while raw-preedit preferences activate at count 3. Consequently heuristic ranking, HTTP `known_preferences`, replay, and clicked analysis cannot accidentally reactivate retained low-count candidate evidence supplied by an older or custom request producer. One-count corrections are different: they remain visible to a clicked model as evidence, while local correction borrowing and generalized patterns still require repeated evidence. Existing segment-chain rows are treated as evidence for candidate ranking and typo correction, not emitted back as new learning rows. If the request shows a `pending_segment` from a prefix commit and the user has explicitly moved to a non-leading suffix candidate, the adapter emits a `segment_chain` row for the combined phrase. A passive `selected_candidate 0` default highlight remains `awaiting-suffix-confirmation`; if the user commits that top suffix, the core state machine can learn the confirmed chain after the commit. The generated custom-wrapper template demonstrates the same two segment-chain paths: replaying existing chain evidence and confirming a pending prefix/suffix chain. It also exposes preedit-leading key context as shell variables and debug rows, matching the OpenAI/Ollama adapter's `behavior_summary.preedit_leading_context`. This lets a click-triggered Analyze action learn from the candidate the user has already navigated to, without running a background model or requiring a cloud provider.

Candidate display state also lives in `State`. The full candidate list stays available for selection and ranking, while `visibleCandidates()` exposes a one-row collapsed list by default and the full list after `Down` expands it. `State` also owns the highlighted candidate index, so arrow-key movement, visual highlight, and `Space` commit target stay aligned.

Candidate selection supports prefix commits for long preedits. `State::refreshCandidates()` inserts a bounded set of useful prefix candidates while retaining the base decoder's complete sentence first. Exact user-dictionary order is protected. Prefix-only learned rows such as `yixia -> 一` cannot outrank a complete phrase. Choosing `继续` from `jixuzuo` records the actual `jixu -> 继续` prefix and leaves `zuo`; it does not train `继续` as a full `jixuzuo` candidate.

One best candidate per useful prefix length is promoted, while a few alternatives remain at the tail for collapsed-row backfill. Single-character options come from the active dictionary backend rather than a hand-written syllable table. A suffix that is only a partial final syllable, such as the `w` in `geciw`, is preserved as unfinished input instead of being deleted as a typo. If the whole tail is noisy, TiPE still exposes at most the first two recoverable prefix chunks. Common English tokens such as `github`, `chatgpt`, and `ollama` are valid segmentation units, so mixed candidates can be selected without losing their remaining pinyin. Direct numeric/mouse selection and `Space` after navigation use the same consumed-prefix metadata.

Long-sentence divergence filtering derives bounded prefix heads from both exact dictionary rows and the active decoder. It orders coherent long candidates first, short selectable prefixes second, and unrelated long guesses last. LibIME lookup records both broad confidence and a stricter decisive lead based on exact full pinyin plus score margin. A decisive sentence bypasses prefix-continuation and divergence heuristics; a near-tied homophone remains eligible for those checks. This keeps simplified LibIME sentences aligned even when an exact Rime prefix is traditional, while retaining the short-prefix escape path when no coherent full sentence exists.

`Engine::updatePanel()` maps that state to fcitx5 preedit updates. When the active UI is `tipeui`, it sends one complete TiPE candidate stream through fcitx5's input panel for every frontend, plus a small aux state marker for expanded/collapsed, supervision, and continuous mode. Some DBus toolkit contexts, including browser text fields, advertise fcitx's `ClientSideInputPanel` capability; the default fcitx dispatch would let the client replace TiPE's panel with its own renderer. For only those contexts, the engine installs fcitx's custom input-panel callback and invokes `tipeui` through an exported addon function while leaving client preedit enabled. The callback already runs in fcitx's deferred UI phase, so it must not requeue the same component through the UI manager. This is a capability-based route, not an application-name exception. `tipeui` chooses the compositor popup for `wayland_v2` and its GTK layer-shell frontend fallback for XIM, DBus, and other contexts. Both therefore consume the same candidate objects and selection callbacks instead of letting the engine maintain a feature-reduced parallel snapshot state. When `tipeui` is not active, the older engine/native diagnostic paths remain available. TiPE keeps ordering, highlight, and numeric selection in its own state so every surface stays aligned with commit behavior.

Switching to TiPE's internal English mode hides the Chinese panel but retains the current `State`, so returning to Chinese mode in the same field restores a half-typed pinyin sequence. `wayland_v2` contexts show the internal `Eng` status through the same cursor-following compositor popup. Other frontends use the UI addon's short-lived GTK status surface. Because `tipeui` owns both surfaces from the same input panel, a mode change does not also publish a second native indicator.

Switching away from TiPE hides the panel but keeps the active input context's preedit state, so a half-typed pinyin sequence can be restored when switching back to TiPE in the same text field. A 300 ms focus-transfer guard suppresses redundant activation indicators when fcitx moves TiPE between input contexts; it does not create a detached status process. Some frontends destroy and recreate the input context during input-method switching, so the engine also keeps a short-lived queue of restorable `State` snapshots with frontend, program, display, and surrounding-text fingerprints before `InputContextDestroyed` drops the old context-owned state. Activation searches the newest matching snapshot first, so switching through another window does not overwrite the only saved preedit. A snapshot is restored only when it is recent and still matches the new input context; if surrounding text is available and clearly differs, TiPE rejects that snapshot, but if the frontend cannot provide surrounding text during activation, TiPE falls back to the program identity and tolerates frontend/display metadata changes instead of discarding the user's half-typed pinyin. Restoring the full `State` preserves the candidate list, highlighted candidate, expansion state, and in-memory supervision context rather than reconstructing only the raw preedit string. This keeps input-method switching from swallowing pinyin while reducing stale state leaks into a later window or unrelated text field.

`tipeui` is the real-use UI owner. For `wayland_v2` it renders TiPE's dark panel on an input-method-v2 popup using stable logical dimensions and a scale-aware shared-memory buffer. Its GTK fallback calls the same `candidate_render.h` Cairo/Pango implementation, so all frontends share fonts, colors, clipping, preedit cursor, cell geometry, number labels, status rendering, pointer hover, and click selection. Clicks return `select`, snapshot serial, and candidate index over a private pipe; `tipeui` verifies the serial and current candidate text before invoking the existing candidate callback. Wayland placement waits for compositor `text-rect` callbacks because that rectangle is surface-local and suitable for the input popup, but not for layer-shell margins. The GTK path first trusts rectangles inside a logical monitor and scales only out-of-bounds physical client coordinates. XIM's standard zero-dimension spot location is converted to a one-by-22 logical caret. If XIM reports `0,0,0,0`, the helper first resolves the active X11 window's `_NET_WM_PID`. A same-user Wine preloader PID supplies its own `WINEPREFIX`; TiPE starts one event-driven `tipe-wine-caret-bridge.exe` in that prefix and sends a serial-numbered query only when a candidate snapshot changes. The Windows helper calls the standard MSAA `OBJID_CARET` location API, reports only an IMM-context boolean with the rectangle, returns no text, and blocks on its input pipe between queries. The GTK process consumes replies asynchronously, rejects zero, invalid, and stale rectangles, and maps accepted physical coordinates using the Xwayland root-to-GTK desktop ratio. An IMM-aware control owns its rendered preedit, so TiPE trusts the reported MSAA caret directly. A control without IMM support receives a transparent, input-inert pinyin overlay at the MSAA insertion point, and the candidate anchor advances by the same Pango-measured text width before TiPE's edit cursor. This explicit contract does not infer rendering behavior from fractional-scale accessibility movement. It never invokes Wine per key and never identifies an application by name. If no bridge was built, the active process is not Wine, or MSAA exposes no caret, the helper queries the X11 pointer once, keeps that stable preedit origin for the composition, and adds the Pango-measured width before TiPE's edit cursor on every snapshot. Because Xwayland coordinates may be physical even when they still happen to fit inside the logical monitor bounds, both Wine and pointer fallbacks compare the X11 root dimensions with the GTK logical desktop explicitly. Near a monitor's right edge, placement flips the popup leftward and right-aligns it to the caret so later measured movement remains visible without crossing the monitor guard. Non-XIM zero-size sentinels remain invalid. A per-input-context tracker observes whether any other usable client rectangle moves with the preedit cursor; only a proven static rectangle receives the same measured X offset. These decisions are frontend/protocol based, never application-name based. Normal input does not append geometry logs; `TIPE_DEBUG=1` enables bounded diagnostics.

Empty-panel UI updates hide only the popup owned by that input context, so a delayed clear from a previous window cannot hide a newer window's candidates. Live supervision snapshots use the same ownership rule: destruction or reset of an old context cannot remove the current context's request file. A real input-context switch destroys and recreates the Wayland popup surface. This prevents a queued text rectangle from the previous field from becoming the first accepted position for the new field and then making the panel jump when the correct rectangle arrives.

`tipe-candidate-window` is the GTK4 fallback used by non-`wayland_v2` frontends and a standalone snapshot diagnostic. Snapshot metadata carries the preedit cursor, static/live classification, pointer-fallback flag, snapshot serial, expanded/selected state, supervision counters, and continuous mode. Its drawing area uses the same visual-cell and Cairo/Pango renderer as the native popup. A motion controller supplies hover state, and a primary-button gesture writes a snapshot-qualified selection event to the UI addon. `tipe-state-probe --snapshot` covers state-to-protocol output, while `tipe-candidate-window --parse-snapshot` covers decoding, edge prediction, and monitor-clamped placement. The persistent helper hides and resets on a clear snapshot and is restarted after either protocol pipe fails. `TIPE_NATIVE_FOLLOW_FALLBACK=1` remains a native-panel diagnostic for runs where `tipeui` is not active. The user install also refreshes addon-directory compatibility copies of `libtipe.so` and `libtipeui.so` because some user-addon setups discover metadata there but do not search the user library directories.

`State::debugSnapshot()` exposes a compact in-memory diagnostic view with preedit, candidate counts, display row counts, expansion state, and event counters. It is meant for tests and future debug tooling; it does not expose raw persisted key history.

`Engine` is the fcitx5 engine addon. It filters release events, maps normalized `ev.key().sym()` values to state-machine actions, treats `F9` as the explicit rerank trigger while composing, and treats `Shift+F9` as a global continuous-mode toggle. Continuous mode reuses the supervised key stream and triggers only the built-in lightweight rerank when the preedit changes; it keeps the panel collapsed and does not invoke external model commands. Pass-through keys observed with no active preedit still refresh the live supervision snapshot with an empty preedit, candidates row, key trail, and event counts, so the supervision/analyze window can inspect broad keyboard behavior without accepting those keys or showing a candidate popup. The engine passes `InputContext::program()` into explicit model requests as application context, uses `Down/Up` as row movement in the expanded six-column candidate grid, updates client preedit, publishes the complete candidate list whenever `tipeui` is active, and commits text through `InputContext::commitString()`. Native or engine-owned fallback output is retained only for diagnostic runs without `tipeui`.

`tipeui` never performs a synchronous Wayland roundtrip from a UI update. Registry discovery remains asynchronous and retries popup creation after the compositor and shared-memory globals arrive; popup creation only flushes outgoing requests. This matters because fcitx defers input-panel updates in an internal list: dispatching nested compositor events while that list is being flushed can destroy an input context and invalidate the list iterator. Popup ownership, engine timers, deferred fallback updates, and asynchronous model jobs use fcitx trackable input-context references, with an explicit destruction watcher removing popup surfaces before queued redraws can inspect them.

Candidate lookup is backend-oriented rather than a hand-filled demo dictionary: user TSV entries override, LibIME provides normal sentence decoding, libpinyin is a fallback, installed Rime dictionaries provide bounded exact/custom data, and the built-in fallback contains only a few basic entries. Extended historical behavior data lives only in the test fixture. External AI remains click-triggered by default; continuous mode uses only bounded in-process ranking.

Default system Rime exact entries are supplemental when LibIME has a language-model result; they do not replace that first result. An explicit user dictionary row or `TIPE_SYSTEM_RIME_DICTIONARY` override still has intentional priority. Complete and unfinished single-syllable input also promotes single-character candidates ahead of backend phrase completions, avoiding long learned or dictionary phrases as the first result for an initial such as `s` or `j`.
